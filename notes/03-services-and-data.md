# Services and data layer

**Date:** 2026-08-11
**Status:** done — a customer can buy a shirt, `make test` proves it

---

## What runs

```
browser
  │ https://localhost/
  ▼
Istio gateway
  ├── /api/auth      ──▶ auth-svc      ──▶ MariaDB, Redis (sessions)
  ├── /api/products  ──▶ order-svc     ──▶ MariaDB
  ├── /api/orders    ──▶ order-svc     ──▶ MariaDB
  ├── /api/payments  ──▶ payment-svc   ──▶ order-svc, mock-payment, MariaDB
  ├── /dummy         ──▶ dummy
  └── /              ──▶ web-ui (Next.js)

mock-payment  — no route, stands in for an external bank. payment-svc calls
                it at http://mock-payment.demo.svc.cluster.local; nothing
                outside the mesh can reach it directly.

platform-config — no route, no pod. Renders one ConfigMap, `app-config`, that
                   the six services above mount for shared env: DEPLOYMENT_ENV,
                   SVC_PREFIX, SVC_VERSION, REDIS_ADDR,
                   OTEL_EXPORTER_OTLP_ENDPOINT/PROTOCOL.
```

| Namespace | What |
|---|---|
| `demo` | 5 routed services + mock-payment (unrouted) + platform-config (ConfigMap only, no pod) — 7 Helm releases, 6 workloads |
| `data` | MariaDB, Redis |

Data sits in its own namespace so NetworkPolicy is written about namespaces,
not individual pods. `platform-config` has `services: {}` in its
`values.yaml` on purpose — a shared key restarts six pods at once, so it's
nobody's value to set from inside their own chart. Not a seventh service.

## The purchase

Five requests, four services:

```
POST /api/auth/login            → token
GET  /api/products              → 6 shirts
POST /api/orders                → order, status pending
POST /api/payments              → payment-svc calls order-svc, the bank,
                                  then order-svc again
GET  /api/payments/:id/success  → status paid
```

`make test-checkout` runs it and then reads the `orders` and `payments` rows
directly. A handler can return 200 on a transaction that rolled back, so the
database is checked rather than the response believed.

## Credentials

Generated by `make secrets`, never in git:

| Secret | Where | Holds | What breaks if wrong |
|---|---|---|---|
| `mariadb` | `data` | root password, app user and password | wrong DSN on init: schema never applies, every service starts against empty tables |
| `app-secrets` | `demo` | the DSN built from the above, JWT signing key | rotated key mid-run invalidates every live session at once |

Created once, left alone — regenerating rotates the password out from under a
database that still has the old one.

Schema and seed: `storage/mariadb-init.sql`, applied by a Job (Kubernetes has
no entrypoint hook like Compose). Every statement is `IF NOT EXISTS` /
`INSERT IGNORE`, so re-applying is safe.

## Probes

Liveness and readiness hit the same path on purpose — `/healthz` only answers
"process alive". A readiness check that also pinged MariaDB would take every
service out of rotation on one database blip.

| | Path | Delay | Period | What breaks if wrong |
|---|---|---|---|---|
| liveness (auth/order/payment/mock-payment) | `/healthz` | 10s | 15s | too short restarts a pod that's merely slow to start; too long leaves a stuck pod serving errors |
| readiness (same four) | `/healthz` | 5s | 5s | too aggressive routes traffic to a pod before it can actually answer |
| web-ui | `/` (no `/healthz` in Next.js) | 10s / 5s | 15s / 5s | same as above |
| dummy | `/healthz`, `/readyz` split | 0s / 0s | 10s / 5s | exists only to demonstrate the split — no real dependency to guard |

Template defaults (`_deployment-rollout.tpl`):

- `timeoutSeconds: 3` — Kubernetes' default 1s fails a pod that's merely busy
- `hasKey`, not `default`, for delays — `default 10` would rewrite an explicit
  `initialDelaySeconds: 0` (dummy) into a 10s wait, since Go templates treat
  `0` as empty

`/healthz` is registered before any middleware — no auth, no fail injection.
Application logic can't fail a liveness probe and restart the pod for the
wrong reason.

## Resources and security context

Every container has both requests and limits — requests are what the scheduler
packs against, limits stop one service starving the node. Set per
`values.yaml`, rendered by one template.

| Tier | requests | limits | What breaks if wrong |
|---|---|---|---|
| auth / order / payment / web-ui | 50m, 96–128Mi | 500m, 384–512Mi | requests too low overpacks the node; limits too low OOM-kills a Go service under load instead of throttling it |
| mock-payment, dummy | 20m, 32–64Mi | 200m, 128–256Mi | same failure mode, lower stakes — nothing depends on these staying up |

CPU limits run ~10× requests (idle, then spike on a request); memory ~4× (a
Go service that exceeds it gets OOM-killed, not throttled).

Hardening is one block on every container (`_helpers.tpl`), not per-service:

```yaml
allowPrivilegeEscalation: false
readOnlyRootFilesystem: true
runAsNonRoot: true
runAsUser: 10001        # numeric — the kubelet does not resolve names
capabilities: { drop: ["ALL"] }
```

A service opts out by name rather than opting in, so a new chart is hardened
before anyone thinks about it. `web-ui` opts out twice: `uid: 1001` (the
Dockerfile's `nextjs` user, not 10001) and `readOnlyRootFilesystem: false`
(Next.js writes its cache under `.next` at runtime).

`topologySpread` (spreads replicas across the 3 kind nodes) and `pdb: {
minAvailable: 1 }` (keeps one alive through a drain) are per-service values
too. `mock-payment` has neither — single replica, nothing depends on it.

## Tests

One file per usecase. `make test` runs them all, cheapest first.

| | Checks | What it would catch |
|---|---|---|
| `routing.sh` | 10 | a path reaching the wrong service, the catch-all shadowing the API |
| `auth.sh` | 10 | a wrong password being accepted, a missing session id |
| `checkout.sh` | 10 | the purchase breaking anywhere along the chain |
| `o11y-stack.sh` | 16 | a component down, otel-collector with no endpoints so telemetry is silently dropped, a trace that never links payment-svc to order-svc and mock-payment, Grafana assets double-prefixed under `/grafana/grafana` |
| `o11y-journey.sh` | 8 | an order that succeeds while its trace is missing — a purchase nobody can debug afterwards — or logs and traces that do not share a trace id |
| `tls-proof.sh` | 4 | credentials travelling in plaintext |
| `resilience.sh` | 9 | data lost with a pod, requests dropped during a replacement |

`tests/lib.sh` holds the pass/fail helpers so each file is about behaviour,
not bookkeeping.
